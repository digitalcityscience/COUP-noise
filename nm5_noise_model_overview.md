# NoiseModelling 5 Engine Overview

This document focuses on the NoiseModelling 5 engine bundled in the local `NoiseModelling` repository, not on the Flask or Celery wrapper around it.

## What NM5 Is In The Repo

In the `NoiseModelling` repo, the "engine" is not one single function. It is a chain built from:

- `noisemodelling-emission`: computes source emission
- `noisemodelling-pathfinder`: computes propagation paths
- `noisemodelling-propagation`: computes attenuation and receiver levels
- `noisemodelling-jdbc`: connects the acoustic code to spatial database tables
- `wps_scripts`: Groovy entry points that wire those pieces together into runnable processing blocks

By default, NoiseModelling runs against an embedded `H2/H2GIS` database, but the same script model can target `PostGIS/PostgreSQL`.

The important consequence is this:

- NM5 works by reading and writing named spatial tables
- each WPS script has a defined table contract
- the full road-noise workflow is a pipeline of those scripts

## The Native NM5 Road-Noise Pipeline

For the road branch used in this repo, the core NM5 pipeline is:

`BUILDINGS + ROADS -> RECEIVERS/TRIANGLES -> LW_ROADS -> RECEIVERS_LEVEL -> CONTOURING_NOISE_MAP`

In practice the pipeline is assembled from these scripts:

1. `Import_and_Export/Import_File.groovy`
2. `Receivers/Delaunay_Grid.groovy`
3. `NoiseModelling/Road_Emission_from_Traffic.groovy`
4. `NoiseModelling/Noise_level_from_source.groovy`
5. `Acoustic_Tools/Create_Isosurface.groovy`
6. `Import_and_Export/Export_Table.groovy`

Only steps 2 to 5 are the actual acoustic workflow. `Import_File` and `Export_Table` are just I/O around it.

## What NM5 Gets

NM5 expects projected spatial tables in a metric SRID. The scripts explicitly assume table-based inputs.

### 1. Buildings

The propagation step expects a `BUILDINGS` table with:

- `THE_GEOM`: 2D building polygons or multipolygons
- `HEIGHT`: building height
- optional `G`: wall absorption or wall impedance parameter

This table is used by the propagation engine to represent obstacles and facade interactions.

### 2. Roads

The road-emission step expects a `ROADS` table with line geometry plus traffic and surface fields.

Core geometry and identity fields:

- `THE_GEOM`
- optional `PK`
- optional `IDSOURCE`
- optional `PERIOD`

Traffic flow fields:

- either `LV`, `MV`, `HGV`, `WAV`, `WBV` with matching speed fields
- or day/evening/night split fields:
- `LV_D`, `LV_E`, `LV_N`
- `MV_D`, `MV_E`, `MV_N`
- `HGV_D`, `HGV_E`, `HGV_N`
- `WAV_D`, `WAV_E`, `WAV_N`
- `WBV_D`, `WBV_E`, `WBV_N`
- matching speed fields such as `LV_SPD_D`, `HGV_SPD_N`, and so on

Road and traffic modifiers:

- `PVMT`: CNOSSOS pavement identifier
- `TS_STUD`
- `PM_STUD`
- `JUNC_DIST`
- `JUNC_TYPE`
- `SLOPE`
- `WAY`

This is the input contract for `Road_Emission_from_Traffic.groovy`.

### 3. Receivers

The propagation step expects a `RECEIVERS` table with:

- `PK`
- `THE_GEOM`: receiver points

In the normal workflow this table is generated by `Delaunay_Grid.groovy`, not hand-authored.

### 4. Optional Native Inputs

`Noise_level_from_source.groovy` can also consume:

- `DEM`: terrain points for elevation
- `tableGroundAbs`: ground polygons with `G`
- `tableSourceDirectivity`: source directivity patterns
- `tablePeriodAtmosphericSettings`: per-period weather and wind-rose settings

So the native NM5 engine can be much richer than the road-only slice used by this repo.

## What Each NM5 Step Does

### Delaunay_Grid

`Receivers/Delaunay_Grid.groovy` is the spatial sampling step.

It gets:

- a building table
- a source table
- meshing parameters like `maxCellDist`, `roadWidth`, `maxArea`, and receiver `height`

It puts out:

- `RECEIVERS`: receiver points
- `TRIANGLES`: the triangulation used later for contour generation

This step does not compute acoustics yet. It defines where the later propagation result will be sampled.

### Road_Emission_from_Traffic

`NoiseModelling/Road_Emission_from_Traffic.groovy` is the road-source emission step.

It gets:

- the `ROADS` table described above

It puts out:

- `LW_ROADS`

`LW_ROADS` is the native road-emission table. It contains source geometry plus octave-band emission power.

Depending on the road-table format, the output is shaped in one of two ways:

- if the input used `D/E/N` traffic fields, the output carries `HZD*`, `HZE*`, `HZN*` octave-band columns
- if the input used a `PERIOD` column, the output carries `PERIOD` plus `HZ*` octave-band columns

This is the point where traffic flow becomes acoustic source power.

### Noise_level_from_source

`NoiseModelling/Noise_level_from_source.groovy` is the propagation step.

It gets:

- buildings
- sources with geometry and emission spectra
- receivers
- optional DEM, ground absorption, directivity, and atmospheric settings
- propagation parameters such as wall coefficient, reflection order, and source distance limits

It can operate in two native modes:

- `tableSources`: geometry and emission live in the same table
- `tableSources` + `tableSourcesEmission`: geometry and emission are split across two linked tables

It puts out:

- `RECEIVERS_LEVEL`

`RECEIVERS_LEVEL` is the main numeric result table. According to the script contract it contains:

- `IDRECEIVER`
- optional `IDSOURCE`
- optional `PERIOD`
- `THE_GEOM`
- octave-band receiver levels such as `HZ63` to `HZ8000`

Downstream NM5 tooling also uses `LAEQ` from this table as the default scalar field for contour generation.

### Create_Isosurface

`Acoustic_Tools/Create_Isosurface.groovy` is the contouring step.

It gets:

- a result table, usually `RECEIVERS_LEVEL`
- the associated `TRIANGLES` table generated from the receiver-mesh step
- a scalar field, default `LAEQ`
- an iso-threshold list in dB

It puts out:

- `CONTOURING_NOISE_MAP`

This table contains contour polygons classified by:

- `ISOLVL`: integer class index
- `ISOLABEL`: label derived from the threshold ranges

Important detail:

- `ISOLVL` is not itself a dB value
- it is the class index derived from the chosen threshold list

In NoiseModelling's own docs, the default threshold list is:

- `35,40,45,50,55,60,65,70,75,80,200`

In this repo, the wrapper overrides that with:

- `45,50,55,60,65,70,75,200`

So any styling or interpretation of `ISOLVL` depends on the threshold list used when `Create_Isosurface` runs.

## What NM5 Puts Out

If you look at the engine itself, not the wrapper, the main native outputs are these tables:

- `RECEIVERS`
- `TRIANGLES`
- `LW_ROADS`
- `RECEIVERS_LEVEL`
- `CONTOURING_NOISE_MAP`

Their roles are:

- `RECEIVERS`: where noise is sampled
- `TRIANGLES`: mesh used to interpolate contours
- `LW_ROADS`: road-source emission power by octave band
- `RECEIVERS_LEVEL`: propagated sound level at receiver points
- `CONTOURING_NOISE_MAP`: polygonized noise classes for mapping

So the "real" output of NM5 is table-to-table, not JSON-to-JSON.

## Structure Of The NM5 Engine In This Repo

The relevant NM5 code lives under the bundled `NoiseModelling` repo:

- `NoiseModelling/wps_scripts/.../Receivers/Delaunay_Grid.groovy`
- `NoiseModelling/wps_scripts/.../NoiseModelling/Road_Emission_from_Traffic.groovy`
- `NoiseModelling/wps_scripts/.../NoiseModelling/Noise_level_from_source.groovy`
- `NoiseModelling/wps_scripts/.../Acoustic_Tools/Create_Isosurface.groovy`
- `NoiseModelling/noisemodelling-jdbc/.../IsoSurface.java`
- `NoiseModelling/Docs/Architecture.rst`

Conceptually, the engine is structured like this:

- spatial tables hold all input and intermediate data
- WPS Groovy scripts orchestrate the workflow
- JDBC/H2GIS provide the database layer
- NoiseModelling Java libraries perform emission, path finding, and propagation

## How COUP-noise Uses NM5

This repo is only a wrapper around that engine.

What COUP-noise adds:

- fetches buildings, roads, and project area from CityPyo
- reshapes CityPyo GeoJSON into NM5-native `BUILDINGS` and `ROADS`
- launches the headless NM5 runner with a fixed script sequence
- exports `CONTOURING_NOISE_MAP` back to GeoJSON
- renames NM5 `ISOLVL` to API-facing `idiso`
- clips the exported polygons to the project area
- optionally rasterizes the clipped GeoJSON into a PNG

So if the question is "what is the new noise engine?", the strict answer is:

- the new engine is the headless NoiseModelling 5 WPS pipeline from the bundled `NoiseModelling` repo
- `COUP-noise` is just the adapter that feeds that pipeline and repackages its final contour table
